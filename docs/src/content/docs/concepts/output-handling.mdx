---
title: Output handling
description: Receive PDF bytes in memory, as a stream, written to disk, or stored server-side.
---

The SDK gives you four ways to handle a rendered PDF: in-memory bytes, a stream, a write-to-disk helper, or a stored document on the server. Pick the one that matches how your code consumes the output.

## In-memory (`render.pdf`)

```ts
const pdf = await client.render.pdf({
  project: 'billing',
  template: 'invoice',
  data: { invoiceNumber: 'INV-001' },
});
// pdf: Uint8Array — write, upload, return as-is.
```

Best for documents that fit comfortably in process memory.

## Streaming (`render.pdfStream`)

For large PDFs or piping straight to an HTTP response or object store, use `pdfStream` and let the SDK keep memory bounded.

```ts
const stream = await client.render.pdfStream({
  project: 'billing',
  template: 'invoice',
  data: { invoiceNumber: 'INV-001' },
});
// stream: ReadableStream<Uint8Array> — pipe to S3, an HTTP response, or any consumer.
```

## Write to file (`renderToFile`)

The `/node` subexport adds a helper that streams bytes directly to disk with bounded memory. Parent directories are created automatically.

The PDF goes to a temporary file in the target's directory, renamed over the target only once complete: when the render, the download or the write fails, an existing file keeps its content and a missing one is not created. A file that cannot be written throws `PoliPageError` with code `io_error` and the message `Failed to write PDF: <path>: <reason>`, for example `Failed to write PDF: ./invoices/INV-001.pdf: EACCES: permission denied`. `<path>` is the path you passed, never the temporary file, and `<reason>` is Node's own error text; the Node error is the `cause`. It is never retried.

Before the render, so that a path that cannot be written costs no render, `renderToFile` creates the missing parent directories and checks that the parent is a directory your process can write, and that an existing target is a regular file you can write. A read-only file is refused, and so is a target that is not a regular file (a directory, FIFO, socket or device such as `/dev/stdout`), with the reason `not a regular file`. These checks read the file's attributes and never open it. To write a PDF to a pipe or to stdout, read `render.pdfStream` into it instead.

When the path is a symbolic link, the PDF replaces the file the link points to, and the link stays as it is. An existing file keeps its permission bits, without setuid, setgid or sticky. Because the rename puts a new file in place of the old one, two things are not kept: the file's owner and group (the new file belongs to the user running your process) and hard links (another name for the old file keeps the old content).

```ts
import { renderToFile } from '@poli-page/sdk/node';

await renderToFile(
  client,
  { project: 'billing', template: 'invoice', data: {} },
  './out.pdf',
);
```

## Server-side storage (`render.document`)

When you want the PDF to live on Poli Page's servers (for later download, preview, or thumbnails), use `render.document`. It returns a descriptor with `documentId`, `presignedPdfUrl`, and a `downloadPdf()` method.

```ts
const doc = await client.render.document({
  project: 'billing',
  template: 'invoice',
  data: { invoiceNumber: 'INV-001' },
});
const pdf = await doc.downloadPdf();
```

`presignedPdfUrl` has a 15-minute TTL. If it expires, call `documents.get(documentId)` to refresh.

## Example

```ts
import { PoliPage } from '@poli-page/sdk';
import { renderToFile } from '@poli-page/sdk/node';

const client = new PoliPage({ apiKey: process.env.POLI_PAGE_API_KEY! });

await renderToFile(
  client,
  { project: 'billing', template: 'invoice', data: { invoiceNumber: 'INV-001' } },
  './invoices/INV-001.pdf',
);
```
